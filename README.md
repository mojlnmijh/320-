你这次的关键词比上次多了一个"存酒"——这是酒吧、KTV、餐吧等业态的刚需功能。加上生鲜、奶茶、堂食扫码、收银台、双端支付，这已经是一套全业态餐饮 SaaS 需求。下面重点拆解存酒功能，并梳理全场景架构。

一、存酒功能：容易被忽略的刚需
"存酒"是酒水消费场所（酒吧、KTV、餐吧、夜店）的核心功能，逻辑与普通点餐差异很大：

业务逻辑

顾客购买整瓶酒，未喝完可寄存

下次到店凭手机号/会员码/二维码取酒

存酒有有效期（如30天、90天），过期处理需规则

支持转赠给朋友、合并多瓶、部分取用

技术实现

wine_storage 表：会员ID、门店ID、酒品、数量、存入时间、有效期、状态

取酒记录：wine_record，记录每次取用

存酒凭证：二维码或会员码，扫码核销

到期提醒：短信/小程序推送

跨店取酒（连锁场景）：需支持

多店版的难点

存酒是否跨店通用？需在总部配置规则

不同门店库存如何核算？

转赠后归属如何变更？

这个功能看似小，却是酒水业态的差异化竞争力，普通点餐系统往往没有，选型时要专门确认。

二、全业态的商品模型抽象
你要同时支持生鲜、奶茶、酒水、正餐，商品模型必须高度可配置：

业态	核心属性	系统能力
正餐	桌台、加菜	桌台管理、并桌、催单
奶茶	规格加料	少冰半糖、叫号、自提
生鲜	称重、库存	称重计价、冷链、预售
酒水	存酒、整瓶	存酒、取酒、转赠
核心结论：一套系统想通吃，必须在规格、加料、称重、库存、存酒上做抽象，用配置而非写死。否则奶茶的"少冰半糖"和生鲜的"按斤称重"无法兼容。

三、单店版 vs 多店版
单店版

一套菜单、一个收银台、一个后台

数据模型简单，部署轻量

适合：单店、夫妻店、小连锁起步

多店版（连锁/加盟）

总部 → 门店 → 桌台 三级结构

总部维护标准菜品，门店可覆盖价格、库存、上下架

订单带 store_id，报表按门店聚合

权限分级：总部 / 区域 / 店长 / 员工

跨店会员、跨店优惠券、储值通用、跨店存酒取酒

技术关键：所有业务表带 store_id，服务层强制注入过滤，越权测试必做。

四、堂食扫码 + 外卖 + 收银台
堂食扫码

桌码 URL 带 store_id + table_id

扫码进店 → 点餐 → 下单 → 支付 → 加菜 → 结账

支持并桌、换桌、催单

外卖

地址、距离、运费、配送范围

自提 / 配送 / 堂食三模式

对接达达、美团配送、自配送

收银台（资金核心）

多种支付：现金、微信、支付宝、会员余额、组合支付

挂单/取单、退款、部分退款

离线收银：断网不停业，恢复后同步

交接班对账，防舞弊

前台小票 + 后厨分单打印

存酒核销集成到收银台

五、微信 + 支付宝双端
方案一：UniApp 一套代码双端

优点：维护成本低

难点：支付、授权、分享 API 不同，需条件编译

适合：中小规模

方案二：两端独立开发

优点：体验最优

缺点：维护成本翻倍

适合：大品牌

支付对接

微信支付：小程序支付、服务商模式（多店分账）

支付宝：小程序支付、当面付

回调必须验签，订单幂等，防重复支付

六、技术架构
前端

MySQL + Redis + 消息队列

分账对接微信服务商、支付宝

打印对接云打印机（飞鹅、易联云）

关键第三方

支付（微信 + 支付宝，多店需分账）

云打印、电子发票

配送（达达、美团配送）

地图、短信、实名

七、选型与落地要点
1. 是否支持存酒
这是酒水业态的刚需，确认是否含存酒、取酒、转赠、到期提醒、跨店通用。

2. 是否支持多业态
商品模型是否支持规格、加料、称重、库存、存酒。

3. 单店多店是否同一套代码
能否配置切换，多店数据隔离是否可靠。

4. 收银台是否完整
离线收银、交接班对账、退款权限、打印稳定性、存酒核销。

5. 双端支付是否打通
微信 + 支付宝是否都支持，多店是否支持分账。

6. 版权与授权

后端是否加密，能否二次开发

是否正版授权，能否商用

7. 安全与合规

多店数据隔离、越权测试

支付回调验签、订单幂等

用户信息加密，符合《个人信息保护法》

上线前渗透测试

八、落地路径建议
分期建设：

一期：单店堂食扫码 + 外卖 + 收银 + 存酒跑通

二期：多门店、总部菜品库、权限分级、跨店存酒

三期：跨店会员、分账、双端支付、数据大屏
